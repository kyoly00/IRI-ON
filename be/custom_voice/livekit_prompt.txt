가능합니다. 그리고 이 프로젝트는 **LiveKit Agents를 fork해서 내부를 뜯어고치는 방향보다, LiveKit을 Realtime Runtime kernel로 두고 public extension point 위에 부족한 모듈을 얹는 구조**로 가는 게 맞습니다.

사용자가 정리한 목표 자체가 이미 `오디오 수신 → 신호 처리 → 턴 감지 → STT → 추론/도구 → TTS → 재생`의 full-duplex 구조이고 , 여기에 FSM·backchannel·resampling·prosody bridge·PII redaction·E2E tracing까지 추가하려는 구조입니다.   

제가 설계한다면 최종 구조를 아래처럼 잡겠습니다.

# 2. 기능별로 어디까지 LiveKit을 쓰고 무엇을 추가할 것인가

| 기능                    | LiveKit 코드 레벨                         |        판정 | 최종 구현                          |
| --------------------- | ------------------------------------- | --------: | ------------------------------ |
| Audio transport       | LiveKit Room / WebRTC                 |         ✅ | 그대로 사용                         |
| Audio capture         | `RoomIO`                              |         ✅ | 그대로                            |
| Audio frame config    | `AudioInputOptions`                   |         ✅ | 24kHz/mono 기준 설정               |
| Noise suppression     | `noise_cancellation` FrameProcessor   |         ✅ | LiveKit/Krisp 또는 client WebRTC |
| AGC                   | `AudioInputOptions.auto_gain_control` |         ✅ | 그대로                            |
| AEC                   | WebRTC + `aec_warmup_duration`        |        🟡 | client AEC + LiveKit warmup    |
| Jitter buffer         | WebRTC media stack                    |         ✅ | 직접 재구현 X                       |
| Resampling            | `rtc.AudioResampler`                  |         ✅ | 24/48k→16k sidecar             |
| VAD                   | LiveKit VAD/Silero                    |         ✅ | 그대로                            |
| Semantic turn         | LiveKit TurnDetector                  |         ✅ | cloud baseline                 |
| Local audio turn      | 없음/제한                                 |        🔧 | **Pipecat Smart Turn**         |
| Endpointing           | `AudioRecognition`                    |         ✅ | 그대로                            |
| Interruption          | `TurnHandlingOptions`                 |         ✅ | 그대로                            |
| False interruption    | AgentActivity                         |         ✅ | 그대로                            |
| Adaptive interruption | LiveKit inference                     |   ✅/Cloud | baseline                       |
| STT                   | `Agent.stt_node()`                    |         ✅ | provider 교체 가능                 |
| Streaming STT         | STT stream abstraction                |         ✅ | GPT/Deepgram 등                 |
| Prosody → LLM         | 범용 기능 없음                              |        🔧 | **custom ProsodyBridge**       |
| Streaming PII         | 범용 middleware 없음                      |        🔧 | **custom STT wrapper**         |
| LLM                   | `Agent.llm_node()`                    |         ✅ | GPT-5.x/OpenClaw               |
| LLM streaming         | AsyncIterable `ChatChunk`             |         ✅ | 그대로                            |
| Session/context       | `AgentSession`, `ChatContext`         |         ✅ | + long-term memory             |
| Function tools        | LiveKit `function_tool`               |         ✅ | 그대로                            |
| Parallel tool         | tool executor                         |         ✅ | 그대로                            |
| Async tools           | `_ToolExecutor`                       |         ✅ | public API 통해 사용               |
| Tool cancellation     | `ToolFlag.CANCELLABLE`                |         ✅ | 그대로                            |
| MCP                   | `MCPToolset`                          |         ✅ | 그대로                            |
| Tool progress         | `RunContext.update()`                 |         ✅ | 그대로                            |
| Dead-air filler       | `RunContext.with_filler()`            |         ✅ | 그대로                            |
| TTS                   | `Agent.tts_node()`                    |         ✅ | provider 교체                    |
| Streaming TTS         | TTS stream                            |         ✅ | 그대로                            |
| Text chunking         | TTS StreamAdapter                     |         ✅ | 추가 최적화 가능                      |
| Playback              | RoomIO/SpeechHandle                   |         ✅ | 그대로                            |
| Barge-in cancel       | SpeechHandle                          |         ✅ | 그대로                            |
| Central FSM           | user/agent state는 존재                  |        🟡 | 상위 Orchestrator 추가             |
| Agent backchannel     | 내부 hook 존재                            |        🟡 | public custom engine 추가        |
| Error handling        | AgentSession error events             |         ✅ | + provider fallback            |
| Reconnect             | LiveKit RTC                           |         ✅ | client session restore         |
| Latency metrics       | metrics package                       |         ✅ | E2E trace 추가                   |
| Speech nuance         | 원음 S2S가 아님                            | ❌ 완전대체 불가 | prosody bridge로 근사             |

LiveKit의 `AgentSession` 설명 자체가 STT, VAD, TTS, LLM과 media stream을 연결하고 turn detection, endpointing, interruption, multi-step tool calling까지 관리하는 runtime이라고 명시합니다. 즉 이 프로젝트의 kernel로 쓰기에 상당히 정확하게 맞습니다. ([GitHub][2])

가장 중요한 클래스입니다.

AgentSession(

    vad=...,
    llm=...,
    tts=...,
    turn_handling=...,
    ...

구조입니다. ([GitHub][2])

따라서 Realtime API의:

과 대응시키면 됩니다.

session = AgentSession(

까지만 LiveKit에 맡깁니다.

# 6. Resampling은 sidecar를 둔다

사용자 문서에서 지적한 것처럼 모델별 sample rate가 다릅니다. 

예를 들어 내부 표준을 이렇게 잡겠습니다.

```text
LiveKit transport : 24 / 48 kHz
                       │
                       ├─────────► playback
                       │
                       ▼
                 AudioNormalizer
                       │
                   16 kHz mono
                 /      |       \
                /       |        \
              VAD    SmartTurn   Prosody
```

LiveKit 자체 예제에서도 `rtc.AudioResampler`를 실제로 사용합니다. ([GitHub][4])

따라서 별도 FFmpeg process 같은 건 넣지 않고:

```python
rtc.AudioResampler(
    input_rate=input_rate,
    output_rate=16000,
)
```

계열로 통일합니다.

# 7. 핵심 ② AudioRecognition이 입력 orchestration을 이미 한다

`audio_recognition.py`의 `AudioRecognition`이 굉장히 중요합니다.

현재 내부적으로:

```text
_audio_input_atask
_commit_user_turn_atask
_stt_consumer_atask
_vad_atask
_end_of_turn_task
```

를 별도 async task로 관리합니다. ([GitHub][5])

즉 우리가 전에 이야기했던:

```text
Audio loop
VAD loop
STT loop
Turn loop
```

가 이미 나뉘어 있습니다.

그리고:

```text
_audio_transcript
_audio_interim_transcript
_audio_preflight_transcript
```

까지 따로 유지합니다. 특히 preflight transcript는 **turn이 완전히 끝나기 전에 generation을 시작하는 preemptive generation** 용도로 존재합니다. ([GitHub][5])

이건 latency 실험에 아주 좋습니다.

# 8. STT는 `stt_node()`에서 확장한다

LiveKit에서 가장 좋은 extension seam 중 하나입니다.

```python
Agent.stt_node(
    audio: AsyncIterable[AudioFrame],
    model_settings
)
```

입니다.

공식 코드에서도 이 메서드를:

> preprocessing, buffering, alternative STT strategy를 위해 override할 수 있다

고 명시합니다. ([GitHub][6])

그래서 프로젝트에서는:

```python
class JarvisAgent(Agent):

    async def stt_node(self, audio, model_settings):

        stream = super().stt_node(
            audio,
            model_settings
        )

        async for event in stream:

            event = pii_filter(event)

            telemetry.record(event)

            yield event
```

같은 wrapper를 만듭니다.

즉 STT를 fork하지 않습니다.

# 9. PII redaction은 여기 끼운다

사용자가 정의한 요구는 **Partial transcript 단계부터 개인정보를 제거해서 LLM과 logging으로 넘어가지 않게 하는 것**입니다. 

그러면:

```text
Streaming STT

INTERIM
"제 주민번호가 900101-1..."

        ↓

PIIRedactor

"제 주민번호가 [RRN]..."

        ↓

FINAL
"제 주민번호가 [RRN]입니다."

        ↓
LLM
```

로 만듭니다.

구조:

```text
Agent.stt_node()
       │
       ▼
 ┌──────────────┐
 │ PIIRedactor  │
 ├──────────────┤
 │ regex        │
 │ NER          │
 │ Presidio     │
 └──────┬───────┘
        ▼
 sanitized SpeechEvent
```

여기서 주의할 점은:

**클라우드 STT를 쓰면 원음 자체는 이미 STT provider에 전달된 뒤입니다.**

따라서:

```text
STT provider에게도 PII를 노출하면 안 된다
```

라는 요구라면 STT 자체를 local/self-hosted 해야 합니다.

### Mode B — 완전 self-host

# 11. Smart Turn 코드가 놀랄 만큼 단순하다

핵심 inference는:

```text
16 kHz PCM
 ↓
최근 최대 8초 추출
 ↓
WhisperFeatureExtractor
 ↓
ONNX Runtime
 ↓
sigmoid probability
 ↓
p > 0.5
 ↓
turn complete
```

입니다. ([GitHub][8])

그래서 adapter interface를:

```python
class SmartTurnDetector:

    async def predict(
        self,
        audio: np.ndarray
    ) -> TurnPrediction:

        audio = keep_last_8_seconds(audio)

        probability = await self.model.predict(audio)

        return TurnPrediction(
            complete=probability > self.threshold,
            probability=probability,
        )
```

정도로 만들 수 있습니다.

# 14. 그런데 LLM에는 raw feature를 다 보내지 않는다

다음처럼 정규화합니다.

```text
<speech_context>
emotion=frustrated
urgency=high
speaking_rate=fast
confidence=0.81
</speech_context>

환불 신청한 지 일주일 됐는데 왜 아직 안 됐어요?
```

이러면 pure STT cascade보다 S2S의 acoustic context를 어느 정도 복구할 수 있습니다.

단,

> **이것으로 speech-to-speech 모델을 완전히 재현하는 것은 아닙니다.**

Realtime 2.1은 원 audio 자체를 모델 input으로 사용하므로 우리가 추출하지 못한 억양·timing·paralinguistic feature도 활용할 수 있습니다. 현재 모델 역시 noise/silence/interruption/audio behavior 개선을 명시적으로 강조합니다. ([OpenAI Developers][1])

이 차이는 실험에서 따로 측정해야 합니다.

# 16. 여기에는 Fast/Deep Router를 추가하는 게 좋다

최종 JARVIS라면:

```text
                   User turn
                       │
                       ▼
                Intent Router
                   /       \
                  /         \
               FAST         DEEP
                │            │
             GPT-small    GPT-5.x /
                │         OpenClaw
                │            │
                │         Tools/MCP
                │            │
                └──────┬─────┘
                       ▼
                   TTS stream
```

형태가 좋습니다.

예:

```text
"몇 시야?"
→ Fast

"지난주 이메일 찾아서 일정 잡아줘."
→ Deep Agent
```

Realtime API를 대체한다는 목적에서는 이게 오히려 장점입니다.

Realtime 하나에 모든 reasoning을 맡기는 대신 **voice latency와 task intelligence를 분리**할 수 있습니다.

# 17. Tools는 새로 만들 필요가 거의 없다

현재 LiveKit tool executor가 생각보다 많이 구현돼 있습니다.

`tool_executor.py`에는 `_ToolExecutor`가 있고 실제 tool 하나당:

```python
asyncio.create_task(...)
```

를 생성해서 lifecycle을 관리합니다. ([GitHub][10])

그리고 running task를:

```text
call_id
→ task
→ RunContext
→ executor
→ cancellable?
```

형태로 저장합니다. ([GitHub][10])

따라서 별도 TaskManager를 또 만들 필요가 없습니다.

# 18. Cancellation도 이미 꽤 강하다

LiveKit에는 `ToolFlag.CANCELLABLE` 개념이 있습니다.

cancellable tool이 있으면 내부적으로:

```text
lk_agents_get_running_tasks
lk_agents_cancel_task
```

같은 tool도 사용할 수 있습니다. ([GitHub][10])

실제로 cancel은:

```text
call_id lookup
 ↓
cancellable?
 ↓
SpeechHandle interruption 허용?
 ↓
cancel_and_wait(task)
```

형태입니다. ([GitHub][10])

따라서:

> "아 그거 취소해."

같은 voice command까지 구현할 수 있습니다.

# 20. Tool preamble도 새로 만들 필요가 줄었다

최신 LiveKit의 `RunContext`에는 이미:

```python
ctx.update(...)
```

와

```python
ctx.with_filler(...)
```

가 있습니다. ([GitHub][11])

예를 들면 설계상:

```python
async def search_mail(ctx, query):

    async with ctx.with_filler(
        "메일을 확인하고 있어요.",
        delay=1.0
    ):
        result = await gmail.search(query)

    return result
```

같은 방식입니다.

Tool이 진행 상태를 알 수 있다면:

```python
await ctx.update("메일 124개를 찾았습니다.")
```

처럼 중간 결과도 conversation에 넣을 수 있습니다. ([GitHub][11])

즉 사용자 문서의 Tool preamble 요구 는 상당 부분 이미 해결돼 있습니다.

# 31. 실제 Agent 구현도 이런 형태가 된다

개념적으로:

```python
class JarvisAgent(Agent):

    async def stt_node(self, audio, model_settings):
        async for event in super().stt_node(audio, model_settings):

            sanitized = self.pii.redact(event)

            self.telemetry.on_stt(sanitized)

            yield sanitized


    async def llm_node(self, chat_ctx, tools, model_settings):

        enriched_ctx = self.prosody_bridge.inject(
            chat_ctx,
            self.current_prosody
        )

        async for chunk in self.router.generate(
            enriched_ctx,
            tools,
            model_settings
        ):
            yield chunk


    async def tts_node(self, text, model_settings):

        chunks = self.speech_chunker(text)

        async for audio in self.tts.stream(chunks):
            yield audio
```

핵심은 LiveKit pipeline을 부수지 않고:

```text
stt_node
llm_node
tts_node
```

세 extension point에 middleware를 넣는 겁니다. 이 세 node는 공식 코드에서 customization point로 제공됩니다. ([GitHub][6])

# 37. 구현 순서는 4단계가 좋다

**Phase 1은 LiveKit 순정 Cascade**입니다. `RoomIO → Silero → LiveKit TurnDetector → Streaming STT → LLM → function tool → streaming TTS`까지만 구현합니다. 여기서 이미 Realtime API의 70~80% 정도의 functional surface가 나옵니다.

**Phase 2에서 Realtime UX를 복원**합니다. Smart Turn, false interruption, preemptive generation, TTS chunking, async tools, filler/progress, cancellable tools를 켭니다.

**Phase 3이 이 프로젝트의 연구 가치가 가장 큰 부분**입니다. Prosody Bridge, PII middleware, backchannel engine, central dialog orchestrator를 직접 구현합니다.

**Phase 4에서 OpenAI Realtime API와 A/B benchmark**를 붙입니다. 정확도·turn-taking·tool use·latency·cost를 모두 동일 trace schema로 비교합니다.

---

## 이 프로젝트에서 실제로 “직접 만든 것”이 되는 부분

LiveKit을 썼다고 해서 단순 프레임워크 조립 프로젝트가 될 필요는 없습니다. 오히려 경계를 명확히 해야 합니다.

```text
외부에서 가져오는 것

LiveKit
→ realtime transport/runtime
→ VAD/STT/LLM/TTS abstraction
→ tool executor
→ MCP
→ interruption
→ metrics

Pipecat Smart Turn
→ audio-native turn classifier


직접 설계/구현

Audio sidecar architecture
Prosody-to-context bridge
Streaming PII middleware
Backchannel policy
Dialog control plane
Fast/Deep model routing
Tool permission/cancellation policy
Unified trace model
Realtime-vs-Cascade eval harness
Cost/latency profiler
```

이렇게 하면 포트폴리오 메시지도 상당히 명확해집니다.

> **OpenAI Realtime API가 하나의 managed speech-to-speech session 내부에서 해결하는 turn-taking, interruption, tool lifecycle, streaming audio와 session orchestration을 분석하고, LiveKit Agents를 runtime kernel로 사용해 독립적인 STT–LLM–TTS cascade로 재구현했다. Audio-native Smart Turn, prosody preservation, privacy middleware, asynchronous tool execution 및 end-to-end observability를 추가하고 동일 voice-task benchmark에서 Realtime API와 성능·비용 trade-off를 평가했다.**

특히 **LiveKit을 fork하지 않는 것**이 중요합니다. `AgentSession`/`AgentActivity`/`_ToolExecutor` 같은 내부 구현은 상당히 복잡하고 빠르게 변하고 있습니다. LiveKit Agents framework 자체는 Apache-2.0이고, 공개 extension point인 `stt_node`, `llm_node`, `tts_node`, tools/events를 통해 확장할 수 있습니다. Smart Turn도 BSD-2-Clause이므로 이 두 개를 중심으로 하는 게 코드 재사용과 유지보수 측면에서도 가장 깔끔합니다. ([GitHub][14])

**다음 실제 작업 단위는 `LiveKit AgentSession`의 한 턴을 소스 코드 call graph로 완전히 뜯는 것**입니다. 즉 `WebRTC AudioFrame → RoomIO → AudioRecognition → VAD → EOU → STT commit → AgentActivity → llm_node → ToolExecutor → tts_node → SpeechHandle → RoomOutput`에서 **각 함수·클래스·async task가 정확히 어디서 호출되는지 코드 라인 수준의 call flow**를 먼저 정리하면, 그 위에 우리가 수정해야 할 지점이 거의 자동으로 결정됩니다.
